# PEA Sanpatong Safety

ระบบสองหน่วยงาน สันป่าตองและแม่วาง สำหรับ GitHub Pages ไม่มีข้อมูลหรือการเชื่อมต่อของลำพูน ใช้ HTML/CSS/JavaScript modules ไม่ต้อง build ไม่มี dependency ติดตั้งในเครื่องเพื่อเปิดใช้งานหน้าเว็บ

## เปิดระบบ

อ่าน [คู่มือตั้งค่า](SETUP.html) project ปัจจุบันคือ `ppe-sanpatong` และมี Web config แล้ว ห้ามสร้าง project ซ้ำ หากติดตั้งระบบแยกให้สร้าง project ของตนเอง เปิด Email/Password สร้างบัญชีแอดมิน เปิด Realtime Database แบบ Locked mode และ deploy `firebase/database.rules.json` จากนั้นเพิ่ม `/admins/{uid}=true` (boolean) ผ่าน Firebase Console

ใส่ Web config ใน `config.js` แทน null เพื่อใช้ร่วมทุกเครื่อง หรือกรอก JSON ในหน้าตั้งค่าเพื่อใช้เฉพาะเบราว์เซอร์นั้น ไม่มีบัญชีรหัสผ่านเริ่มต้น ห้ามใส่ password, service account key, GitHub token ใน repo

ใช้ Settings → Pages → Deploy from a branch → main → /(root) หน้าเว็บใช้ relative paths จึงรองรับ project Pages ใต้ `/pea-sanpatong-safety/` โดยตรง หรือเผยแพร่ source ผ่าน workflow ที่เหมาะกับหน่วยงาน

## การทำงาน

- ล็อกอินแอดมินก่อนอ่านข้อมูลทั้งหมด ไม่เปิดทะเบียนหรือคลังให้สาธารณะ
- เพิ่มทะเบียน/เปิดปิดคน นำเข้า CSV สูงสุด 500 คนต่อครั้งโดย preview และข้ามรหัสเดิม ดาวน์โหลด template ว่างได้
- เพิ่มอุปกรณ์แยก variant และหน่วยมาตรฐานเป็น SKU ยอดเริ่ม 0
- รับเข้าและเบิกหลายรายการใน transaction เดียว พร้อมประวัติและ server timestamp
- idempotency key ป้องกันคำขอเดิมบันทึกซ้ำใน transaction; ปุ่มยืนยันปิดระหว่างรอบคำขอ
- ปรับยอดพร้อมเหตุผล ตรวจคลังเทียบกับ movement ledger
- ประวัติทั้งหมด CSV/พิมพ์ PDF และ backup JSON

## ข้อจำกัดรุ่นแรก

มีหน้า QR ส่งคำขอพร้อมภาพ และแก้บุคลากร/อุปกรณ์ได้โดยคง IDs เดิม หน่วยนับที่มีประวัติแล้วเปลี่ยนไม่ได้ หน้าเจ้าหน้าที่รับเข้า/เบิกใช้ลิงก์ HTTPS เป็นหลักฐาน ยังไม่มี role viewer/storekeeper แยก ยกเลิกใบเบิกหรือ restore ผ่านเว็บ ผู้จ่ายใช้บัญชีแอดมินเท่านั้น รายการผิดแก้ด้วย adjustment มีเหตุผล ไม่ลบประวัติจาก UI

Realtime Database transaction อ่าน/เขียน `/office` ทั้งก้อน เหมาะระบบเริ่มต้นคลังเดียว ต้องวางแผนย้าย server-side transaction เมื่อข้อมูลมากขึ้น Rules จำกัดสมาชิก admins ซึ่งเป็นผู้มีสิทธิ์เต็ม ไม่ใช่ระบบ immutable audit ที่กันแอดมินดัดแปลงข้อมูลเองได้ ห้ามใช้จำนวนผลต่างเป็นหลักฐานว่าของหายเสมอ

สำรอง JSON เป็น manual export ไม่ใช่ระบบ scheduled backup หรือ restore ที่ผ่านการทดสอบแล้ว การพิมพ์ PDF ใช้ browser print ไม่ใช่รายงานแบบจัดหน้าเฉพาะ

## คำขอเบิกและ Dashboard ส่วนกลาง

หน้าแรกมี Dashboard ส่วนกลาง ซึ่งต้องเข้าสู่ระบบและแสดงเฉพาะหน่วยงานที่บัญชีมีสิทธิ์ ทุกสถิติอ่านจากข้อมูลคลัง ประวัติ และคำขอจริง ไม่ใช้ยอดจำลอง

- `admins/UID = true` เดิมมีสิทธิ์สันป่าตองเท่านั้น
- เพิ่มผู้ดูแลหลายหน่วยงานภายหลังใช้ `admins/UID/sanpatong = true` และ/หรือ `admins/UID/maewang = true` ต้องเปลี่ยนค่าเดิม true เป็น object ผ่าน Console เมื่อพร้อม ไม่เปิดสิทธิ์แม่วางโดยอัตโนมัติ
- สันป่าตองยังอยู่ `/office` เพื่อรักษาข้อมูลเดิม แม่วางแยก `/offices/maewang`
- เปิด Firebase Authentication Anonymous และเผยแพร่ `firebase/database.rules.json` ก่อนเปิดรับคำขอ
- แอดมินเปิดเมนูคำขอเบิก กดเปิด/อัปเดตรายการ จะตั้ง `requestEnabled` และสร้าง catalog อุปกรณ์ ไม่มีข้อมูลบุคลากร คำขอในหน่วยงานที่ยังไม่เปิดใช้ถูกปฏิเสธ
- ลิงก์ `request.html?office=sanpatong` สำหรับ QR ของหน่วยงาน
- ผู้เบิกกรอกรหัส/ชื่อ เลือกอุปกรณ์ แนบภาพ JPEG ที่เว็บย่อไม่เกินประมาณ 210 KB แล้วตรวจและส่ง
- คำขอเก็บ `/office/requests/anonymousUID/requestID` ผู้ส่งอ่านได้เฉพาะคำขอของตนเองและ catalog ไม่อ่านทะเบียนหรือประวัติ ไม่เขียนคลัง
- แอดมินตรวจรูปและรหัสกับทะเบียน แล้วอนุมัติใน transaction เดียว: ตัดคลัง + ประวัติ + สถานะ approved + catalog อัปเดตพร้อมกัน หากของไม่พอทั้งใบไม่เปลี่ยน
- ไม่อนุมัติใส่เหตุผล ยอดคลังไม่เปลี่ยน
- หลักฐานภาพอยู่กับคำขอใน Realtime Database ไม่ส่งไป Drive ลำพูนหรือบริการอื่น จึงต้องคำนึงถึงพื้นที่และปริมาณดาวน์โหลดโดยเฉพาะเมื่อมีคำขอจำนวนมาก
- มี App Check แบบ reCAPTCHA Enterprise และ Rules เว้นคำขอ 60 วินาทีต่อ anonymous UID ตรวจ Console วันที่ 12 ตุลาคม 2569: Realtime Database Enforced, Authentication Unenforced การเปลี่ยน UID ยังไม่ใช่การจำกัดต่อคนหรือต่ออุปกรณ์แบบถาวร ไม่อ้างว่าผู้กรอกชื่อคือเจ้าของรหัส ผู้ดูแลต้องตรวจตัวผู้เบิกก่อนจ่าย
- เมนูคำขอเบิกแสดง QR จากลิงก์ของหน่วยงาน ใช้ไลบรารี QRCode.js โหลดผ่าน CDN หาก CDN ถูกบล็อกยังใช้ลิงก์ได้

ต้องทดสอบ Rules กับผู้ส่งจริงก่อนใช้เบิกจ่ายจริง: คำขอสำเร็จ อ่านผู้อื่นไม่ได้ เขียนคลังไม่ได้ อนุมัติและเปิดกลับมายอด/สถานะ/ประวัติตรงกัน

## Dashboard สำหรับประชุม

เปิด `#/dashboard` จากลิงก์ตรงหรือปุ่มหน้าแรก ต้องเข้าสู่ระบบผู้ดูแล ข้อมูลอ่านแบบ realtime จากประวัติการจ่ายของหน่วยงานที่บัญชีมีสิทธิ์ ไม่มีข้อมูลลำพูนหรือข้อมูลจำลอง

ตัวกรอง: หน่วยงาน อุปกรณ์ รหัส/ชื่อผู้เบิก และช่วงวันที่ รวมผู้เบิกไม่ซ้ำและใบเบิกไม่ซ้ำ กราฟหน่วยงาน หมวดอุปกรณ์ รายการ 10 อันดับ และแนวโน้มเดือนเปลี่ยนตามตัวกรองเดียวกับตาราง แยกจำนวนตามหน่วยนับ ไม่บวกรองเท้าคู่กับหมวกใบเป็นยอดเดียว โหมดประชุมซ่อนรหัสและชื่อในตารางและ CSV; PDF ใช้ระบบพิมพ์ของเบราว์เซอร์ สถานะคำขอรออนุมัติแยกจากยอดจ่ายจริง ไม่รวมแม่วางที่ยังไม่เปิดหรือไม่มีสิทธิ์

บัญชี Firebase ใช้ app name คงที่เพื่อคง session หลัง reload ในแท็บเดิม ไม่บันทึกรหัสผ่านเอง

## แก้ไขใบรับเข้า

หน้ารับเข้าและประวัติมีตารางใบรับเข้า เลือก ดู / แก้ไขใบรับเข้า เพื่อแก้เลขเอกสาร วันที่ตรวจรับ หลักฐาน และจำนวนแต่ละ SKU รวมถึงเพิ่มหรือนำรายการออก ระบุเหตุผล ตรวจส่วนต่างและยอดหลังแก้ แล้วกดยืนยัน สามารถยกเลิกทั้งใบโดยเก็บต้นฉบับและประวัติไว้ ไม่ลบประวัติถาวร

ระบบเก็บใบต้นฉบับใน movements และรุ่นแก้ไขพร้อมข้อมูลก่อน/หลังใน receiptRevisions ส่วนต่างที่กระทบคลังเป็น adjustment ที่อ้าง receiptId และ receiptRevisionId เขียนใบแก้และยอดพร้อมกันใน transaction ของหน่วยงาน แก้ข้อมูลเอกสารอย่างเดียวไม่สร้างการเคลื่อนไหวคลัง ป้องกันการแก้รุ่นเก่าและการบันทึกซ้ำ หากลดยอดแล้วคลังติดลบจะไม่บันทึก

นี่เป็นการแก้ยอดรับเข้าตามใบ ไม่ได้จัดสรรการเบิกตาม lot ระบบยังเก็บการเบิกตาม SKU ประวัติการแก้ถูกเก็บโดยแอป; Rules ปัจจุบันยังไม่ได้ทำ audit immutable ฝั่ง server

## แฟ้มเอกสารจัดซื้อและคงคลังแยกหมวด

แฟ้มจัดซื้อหนึ่งแฟ้มต่อหนึ่งชุดจัดซื้อ แยกตามหน่วยงานและปีงบประมาณ รองรับ PDF, DOC/DOCX, XLS/XLSX, JPG/PNG ไม่เกิน 100 MB ต่อไฟล์ เลือกประเภทเอกสารและแนบหลายไฟล์ได้ เพิ่มไฟล์รุ่นใหม่โดยอ้างไฟล์เดิม ไม่เขียนทับต้นฉบับ เก็บรายการ procurements, documents และ receiptFolders ในฐานข้อมูลหน่วยงาน การแก้ใบรับเข้าคงรหัสใบเดิมจึงไม่หลุดจากแฟ้ม

สร้างแฟ้มในเมนูแฟ้มจัดซื้อ แล้วเชื่อมใบรับเข้าเดิม หรือเลือกแฟ้มขณะรับเข้าใหม่ เปิดเอกสารจากใบรับเข้าและ Dashboard ส่วนกลางได้ PDF/รูปเปิดในหน้าต่างเว็บ Word/Excel ดาวน์โหลดต้นฉบับ พื้นที่ใช้แสดงรวมไฟล์ทุกรุ่นของหน่วยงาน

บริการเดิมสำหรับเอกสาร Storage (ยังไม่ได้ติดตั้งสำเร็จ และไม่ได้ใช้สำหรับไฟล์ใหม่): Cloud Functions (safety-documents) ใน asia-southeast1 ตรวจ Firebase Auth, App Check และสิทธิ์ /admins ล่าสุดทุกคำขอ ไม่ใช้ลิงก์ token สาธารณะถาวร ไม่สร้าง role หรือ claims ซ้ำกับฐานข้อมูล Binary อยู่ใน Storage ส่วนตัวภายใต้ documents/{live|qa}/{officeId}/{year}/{folderId}/{documentId}; backend อ่านไฟล์ส่งให้ผู้มีสิทธิ์โดย callable กลุ่มไฟล์และยอดคลังใช้แยก QA/live

ขั้นตอนเก่าสำหรับ Storage เท่านั้น ไม่ต้องดำเนินการสำหรับการเชื่อม Drive ใหม่: ติดตั้งด้วย Firebase CLI หลังเปิด Blaze และ default Storage bucket: firebase deploy --only functions:safety-documents,storage --project ppe-sanpatong โค้ด backend อยู่ functions/ มี package-lock สำหรับติดตั้งซ้ำ กฎ storage.rules ปฏิเสธการเข้าถึงตรงทั้งหมด คงสิทธิ์ Realtime Database เดิม ไม่มีการเปลี่ยน Rules บุคลากรหรือประวัติ

คงคลังแบ่งหมวดตาม zone เดิม มีตัวกรองชื่อ/ไซส์/สีและเหลือน้อย/หมด รับเข้าเป็นยอดสุทธิของใบหลังแก้ไขและยกเลิก จ่ายออกนับใบเบิก และปรับตรวจนับแสดงแยก ผลต่างประวัติควรเป็นศูนย์ ส่งออก CSV ตามรายการที่กรอง และพิมพ์ PDF ได้

## เปลี่ยนเอกสารใหม่ไป Google Drive (13 ตุลาคม 2569)

ไฟล์ใหม่อัปโหลดจากหน้าแฟ้มจัดซื้อผ่าน Google Identity Services และ Drive API เข้า Drive ของ sarinyawannasuwong@gmail.com ใช้สิทธิ์ drive.file เฉพาะไฟล์ที่แอปสร้าง ไม่เก็บ access token ใน localStorage หรือฐานข้อมูล ไม่ขอ client secret ในเว็บ ตัวระบบตรวจบัญชีเจ้าของก่อนอัปโหลด เก็บแต่ข้อมูลรายการและรหัส Drive ใน Firebase เดิม แยกแฟ้ม live/qa และหน่วยงาน เอกสารเก่าที่ไม่มี provider ยังอ่านผ่าน backend เดิม ไม่มีการย้ายหรือลบไฟล์เดิมอัตโนมัติ

การตั้งค่า: เปิด Google Drive API ใน project ppe-sanpatong; สร้าง Google Auth Platform branding และ OAuth client ชนิด Web application; Authorized JavaScript origins ใช้ https://pea-spt.github.io และ http://127.0.0.1:4173 สำหรับทดสอบ; เพิ่มบัญชีเจ้าของเป็น test user หากอยู่โหมด Testing แล้วใส่ public client ID ใน drive-config.js ต้องอนุมัติ User Data Policy และการให้สิทธิ์ Google ด้วยบัญชีเจ้าของก่อนใช้งาน

ผู้ใช้อื่นเปิดลิงก์เอกสารได้เฉพาะเมื่อมีสิทธิ์ใน Drive ด้วย สิทธิ์ Firebase ไม่ได้ให้สิทธิ์ Drive อัตโนมัติ เว็บไม่เปิดไฟล์เป็นสาธารณะหรือเพิ่มผู้ร่วมใช้เอง หากบันทึก Firebase หลังอัปโหลดไม่สำเร็จ ระบบแจ้งรหัสไฟล์ที่เหลือใน Drive ให้ตรวจและกู้คืนก่อนลองซ้ำ ไม่รายงานว่าแนบสำเร็จ

สถานะการเปลี่ยน: ตั้ง OAuth client ID และ Authorized JavaScript origins แล้ว, Drive API Enabled, เพิ่มบัญชีเจ้าของเป็น test user และเผยแพร่ Database Rules แล้ว; เจ้าของลงชื่อเข้าใช้และอนุญาต Drive แล้ว ทดสอบอัปโหลดภาพ QA สองรุ่น บันทึกรายการใน Firebase และเปิดไฟล์จากภาพรวม/Dashboard ส่วนกลางสำเร็จ ยอดคลังและข้อมูล QA ส่วนอื่นไม่เปลี่ยน ผู้ดูแลรายอื่นต้องได้รับสิทธิ์ไฟล์ใน Drive จากเจ้าของก่อนเปิดได้

ทะเบียนบุคลากรแสดงเฉพาะปัจจุบันเป็นค่าเริ่มต้น เปลี่ยนสถานะเป็นปิดใช้งานหรือย้ายได้ โดยสถานะย้ายระบุเดือนและปี พ.ศ. ยอดบุคลากรในภาพรวมและ Dashboard ส่วนกลางนับเฉพาะปัจจุบัน คนที่ย้ายยังค้นดูได้ผ่านตัวกรองย้าย ประวัติการเบิกไม่ถูกลบและยอดคลังไม่เปลี่ยน

## หลักฐานเบิกจ่ายของแอดมิน

หน้าเบิกจ่ายเลือกไฟล์หลักฐานได้โดยไม่บังคับ ระบบบันทึกการจ่ายและยอดคลังก่อนอัปโหลดไป Google Drive หากอัปโหลดไม่สำเร็จ การจ่ายยังคงบันทึกแล้ว และกลับมาลองแนบใหม่ได้จากรายการเบิกจ่ายด้านล่างหรือหน้าประวัติ ต้องเชื่อม Drive ด้วยบัญชีเจ้าของที่ตั้งไว้เช่นเดียวกับแฟ้มจัดซื้อ

ปุ่ม แนบ / แก้ไขหลักฐาน รองรับแนบไฟล์ภายหลัง เพิ่มหลายไฟล์ หรือแนบรุ่นใหม่แทนไฟล์เดิมโดยเก็บต้นฉบับ ไฟล์สูงสุด 100 MB ต่อไฟล์ ข้อมูลไฟล์อยู่ใน movements/{id}/files แยกจากแฟ้มจัดซื้อ แก้วันที่ หมายเหตุ และลิงก์หลักฐานได้พร้อมประวัติก่อน/หลังใน evidenceEdits และตรวจรุ่นข้อมูลเพื่อป้องกันการเขียนทับการแก้พร้อมกัน การแก้ส่วนนี้ไม่เปลี่ยนผู้เบิก รายการอุปกรณ์ จำนวน หรือยอดคลัง สิทธิ์ใช้ Rules แอดมินของหน่วยงานเดิม
